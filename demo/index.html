A11y Guide: Keyboard Navigation

This chart is fully navigable with a keyboard. You don't need a mouse to explore the data, drill into details, or go back.

Keyboard shortcuts

Key Action
Tab / Shift+Tab Move between bars in the chart
Enter or Space Drill into the selected bar to see more detail
Escape Go back one level
Backspace Go back one level (common in data tools like Excel and Power BI)
Alt+← Go back one level (browser-style navigation)

How the chart works

The chart shows trade volumes for 2025. It has three levels of detail:

  1. Year view — 12 monthly bars. Click or press Enter on a month to see its weeks.
  2. Month view — 4 or 5 weekly bars. Click or press Enter on a week to see daily data.
  3. Week view — 5 daily bars (Monday to Friday). This is the most detailed level.

The breadcrumb trail above the chart shows where you are. Click any level in the breadcrumb to jump back to it.

Ways to go back

There are several ways to return to the previous level. Use whichever feels natural:

Method How Notes
Escape Press Escape anywhere on the page Universal convention — works in dialogs, menus, and drill-downs
Backspace Press Backspace when not typing in a text field Familiar if you use Excel pivot tables or Power BI
Alt+← Hold Alt and press the left arrow key Same shortcut as browser back — intercepted here to navigate within the chart
Back button Click the ← Back button above the chart Only visible when you've drilled in
Breadcrumb Click a level name in the breadcrumb trail Jump directly to any level — not just one step back
Swipe right Swipe right on the chart (touch screens) Mobile equivalent of back — matches iOS and Android navigation patterns

Screen reader experience

When you navigate to the chart, your screen reader will announce:

  • The chart title and data summary (range of values, highest and lowest)
  • Each bar's label and value as you Tab through them
  • A live announcement when you drill in or out (e.g. "Showing January 2025: 4 weeks")

A hidden data table is also available for screen readers that prefer table navigation. Use your screen reader's table navigation commands to browse the data in rows and columns.

How It Works

Flare Demo explores two hard problems in canvas-rendered applications: making them accessible, and keeping them visually consistent. Here is what each piece does and why it matters.

Why canvas?

A growing number of web applications render to canvas instead of the DOM — design tools (Figma, Canva), games, maps, and large-scale data visualisations. Canvas gives pixel-level control and GPU-accelerated performance that HTML elements cannot match. The trade-off: assistive technology sees nothing. No buttons, no headings, no data. Flare Demo shows how that trade-off can be addressed.

Mirror DOM

Canvas gives you fast, flexible rendering — but screen readers and keyboards cannot see it. Mirror DOM places invisible interactive elements over each bar so assistive technology works without compromising visual performance. One chart, two layers, zero trade-offs.

Figma and Flutter use the same approach. Flare Demo adapts it for data visualisation, where the natural accessible representation is a data table.

Material M3 Design Tokens

Every colour in Flare Demo comes from a single set of design tokens following Material Design 3 naming. Change the theme once, and the sidebar, headings, and chart bars all update together — even though the canvas cannot read CSS.

M3 uses a colour system called HCT that mathematically guarantees contrast. If the sidebar text is readable, the chart labels are too — same token pair, same guarantee.

Mirror DOM

The problem

Charts built with canvas are fast and flexible — they can render thousands of data points smoothly. But to a screen reader or a keyboard, a canvas is just a blank rectangle. There are no buttons to press, no headings to navigate, no data to read. The entire chart is invisible to assistive technology.

This is the trade-off most charting libraries make: performance for sighted users, silence for everyone else.

The solution: two layers from one source

Flare Demo draws the chart twice — once for the eye and once for assistive technology:

  1. The visual layer is the canvas. It draws the bars, axes, labels, and title that you see on screen.
  2. The accessibility layer is a set of invisible HTML elements placed exactly on top of each bar. These elements have labels, roles, and keyboard handlers — everything a screen reader or keyboard needs.

Both layers come from the same data. When you drill into a month, the canvas redraws and the accessibility elements rebuild in the same step. They never drift out of sync.

This is the Mirror DOM pattern — the visible pixels and the accessible structure are two projections of the same thing.

What you experience

If you are... You interact with...
Using a mouse The canvas directly — click a bar to drill down
Using touch Tap a bar to drill down, swipe right to go back
Using a keyboard The invisible overlay elements — Tab highlights bars, Enter drills down, focus rings appear on the bars
Using a screen reader Labels, a data table, and live announcements — the chart describes itself as you navigate

All three groups navigate the same chart with the same data. The mirror DOM makes this possible without duplicating the application logic.

Who else does this?

Figma uses the same approach for their design editor — every shape on the canvas has a hidden HTML counterpart for screen readers and keyboard navigation. Flutter does something similar on the web, building a parallel semantics tree over its canvas output.

Flare Demo adapts the technique for data visualisation specifically, where the natural semantic representation is a data table rather than a tree of shapes.

Canvas beyond charts — data platform use cases

In a data platform, canvas rendering shows up wherever the DOM can't keep pace with the volume or complexity of what needs to be drawn:

  • Large-scale data grids — virtual scrolling grids (e.g. AG Grid's canvas renderer) where DOM nodes can't keep up with 100k+ rows. The grid draws cells to canvas for performance, but those cells are invisible to screen readers without a mirror layer.
  • Flow and pipeline builders — drag-and-drop DAG editors for ETL/data pipelines (Pentaho, Airflow graph view, Azure Data Factory). Nodes and edges render to canvas for smooth panning and zooming. Each node needs a keyboard-focusable, labelled counterpart.
  • Relationship and lineage graphs — entity graphs showing fund structures, counterparty networks, or data lineage. Force-directed layouts render thousands of nodes on canvas. Without a mirror, the entire graph is a silent rectangle.
  • Geospatial overlays — Mapbox, deck.gl, and similar tools use WebGL to render millions of points on a canvas. Portfolio heatmaps, regional breakdowns, and risk maps all hit this pattern.

Charts and graphs cover the majority of the canvas accessibility problem in data platforms. The mirror DOM pattern proven here applies directly to all of the above — same SemNode tree, different geometry.

Canvas in other domains

The same accessibility gap exists outside data platforms:

  • Design tools — Figma, Canva, Excalidraw (sub-pixel positioning, custom hit testing)
  • Games — browser games via Canvas 2D / WebGL / WebGPU; engines like Unity, Unreal, Godot export to WASM with all UI inside the canvas
  • Creative tools — photo/video editors, audio workstations (timelines, waveforms, pixel manipulation)

All face the same problem: the more complex the canvas application, the harder it is to build the mirror — and the more essential it becomes.

Rendering APIs and input devices

Flare Demo uses Canvas 2D — the simplest rendering API. WebGL (GPU shaders, used by most 3D web apps and mapping tools) and WebGPU (its modern successor, modelled after Vulkan/Metal/DX12) face the same accessibility gap. Whether pixels come from a 2D context, a WebGL shader, or a WebGPU compute pipeline, the screen reader sees nothing. Mirror DOM works at the semantic level, not the rendering level.

The same applies to input devices. The Gamepad API lets web apps read controller input (thumbsticks, buttons, triggers), but gamepads have no concept of focus or ARIA. Mirror DOM provides the bridge — gamepad actions map to the same semantic elements that keyboard actions use.

Technical detail

This section is for engineers interested in the implementation. It explains the architecture and the code path.

Why Rust and WebAssembly?

Flare Demo's renderer is written in Rust, compiled to WebAssembly. A fair question: why not just use JavaScript?

For a 12-bar chart, it doesn't matter. JavaScript draws bars just fine. But Flare Demo explores a pattern that needs to scale to real applications:

  • Predictable performance — Rust compiles to native-speed WASM with no garbage collector. There are no surprise pauses mid-frame. For a chart with 12 bars this is irrelevant; for a chart with 10,000 data points or a 60fps animation, it is the difference between smooth and janky.
  • Memory safety without a runtime — Rust catches out-of-bounds access, use-after-free, and data races at compile time. The WASM module cannot corrupt the browser's memory. JavaScript relies on the engine's runtime checks, which are good but come with overhead.
  • Clear boundary — the WASM module has a narrow, typed interface: data in, geometry out. This forces a clean separation between rendering (deterministic, pure computation) and orchestration (stateful, DOM-touching, async). That boundary is what makes the mirror DOM pattern maintainable.
  • Portability — the same Rust code can compile to native (for a desktop app), to WASM (for the browser), or to a test harness (for CI). The rendering logic is not coupled to the browser environment.

The trade-off is build complexity. You need the Rust toolchain, wasm-pack, and a build step. For a small demo that's overhead; for a production canvas app with thousands of renders per second, it pays for itself.

This is the same bet Figma made — their rendering engine is C++ compiled to WASM. It is also why game engines targeting the web (Unity, Godot) compile their C++/C# cores to WASM rather than rewriting in JavaScript.

Architecture: Rust renders, JavaScript orchestrates

The rendering engine has one job: take data in, draw pixels on the canvas, and return the geometry of what it drew. It knows nothing about the DOM, accessibility, or navigation.

JavaScript handles everything else: loading data, managing the navigation stack, building the mirror DOM, wiring keyboard handlers, and announcing changes to screen readers.

This split means new features (like drill-down, breadcrumb navigation, or keyboard shortcuts) don't require recompiling the WASM module.

The render cycle

Every time the view changes (drill in, drill out, jump via breadcrumb), this sequence runs:

  1. Extract data — pull the right slice from the dataset (e.g. "weeks in March" or "days in Week 2")
  2. Call WASM render() — redraws the canvas and returns semantic nodes as JSON: SemNode[] with role, label, value, and geometry for each bar
  3. Tear down old mirror DOM — remove the previous overlay elements and semantic table
  4. Build new mirror DOM — for each bar rect, create a transparent <div> positioned at the exact pixel coordinates (adjusted for device pixel ratio). Set role="button", tabindex="0", and an aria-label with the bar's value
  5. Build semantic table — a visually hidden <table> with the same data, for screen readers that prefer table navigation
  6. Update breadcrumb and live region — so the user knows where they are and what changed
  7. Move focus — to the first bar overlay, so keyboard users land in the right place

The overlay technique

The canvas sits inside a position: relative container. The overlay layer is position: absolute filling the same space. Each bar overlay is absolutely positioned at the bar's coordinates:

<div class="chart-container" style="position: relative">
  <canvas id="chart" width="700" height="450"></canvas>
  <div class="mirror-overlay">
    <div class="bar-overlay"
         role="button" tabindex="0"
         aria-label="Jan: 1,200 Trades. Click to drill down."
         style="left: 85px; top: 62px; width: 36px; height: 338px">
    </div>
    <!-- one per bar -->
  </div>
</div>

The overlays are transparent — the canvas shows through. But they receive native browser focus, so Tab moves through them and :focus-visible draws a ring on the bar. Click and keyboard events on the overlays trigger drill-down, not the canvas.

Device pixel ratio

The WASM renderer works in canvas pixel coordinates (e.g. 700×450 on a 2× display is actually 1400×900 canvas pixels). The overlay divs need CSS coordinates. The JS divides every bar rect dimension by window.devicePixelRatio when positioning overlays. Get this wrong and the focus rings appear in the wrong place.

What can go wrong

Mirror DOM introduces failure modes that don't exist in regular web UIs:

Failure What happens
Missing mirror A bar exists on canvas but has no overlay — invisible to keyboard and screen readers
Stale mirror Data changed, canvas updated, but the overlays still show the old data
Misaligned mirror Overlay is at the wrong coordinates — focus ring appears in the wrong place
Lost focus After drill-down, focus disappears instead of moving to the new content
Silent transition The chart visually updates but the live region doesn't announce what changed

Flare Demo's ?fail= query parameter lets you toggle each of these failure modes on and off, so accessibility scanners can be tested against known-broken states.

Material M3 Design Tokens

Design tokens: one palette, two renderers

Flare Demo uses a single set of colour values — called design tokens — to style everything you see. The sidebar, the headings, and the chart bars all draw their colours from the same source. When you toggle between light and dark mode, every element updates together because they all read from the same place.

This matters for accessibility. Material Design 3 (M3) defines its colours using a system called HCT (Hue, Chroma, Tone) that mathematically guarantees text will have enough contrast against its background. If the sidebar text is readable, the chart labels are too — because they use the same token pair.

The challenge is that canvas doesn't read CSS. A normal HTML element picks up colours automatically from a stylesheet. A canvas ignores stylesheets entirely — you have to tell it what colour to paint, explicitly, every frame. Flare Demo bridges this gap by reading the CSS tokens from JavaScript and passing them into the rendering engine as data.

How the token pipeline works

Step What happens
1. CSS defines Tokens like --mat-sys-primary and --mat-sys-surface are set as CSS custom properties on the page. Light and dark themes override these values.
2. DOM consumes HTML elements (sidebar, buttons, headings) use var(--mat-sys-primary) in their styles — standard CSS, nothing unusual.
3. JS reads A readTheme() function calls getComputedStyle() to read the current token values as plain strings (e.g. "#386A20").
4. JSON crosses the boundary The token values are packed into a JSON object and passed to the Rust/WASM rendering engine as a function parameter.
5. WASM paints The renderer deserialises the JSON into a typed Theme struct and uses those values in every set_fill_style_str() call — background, axes, bars, labels.

The result: CSS is the single source of truth. Toggle the theme, and both the DOM chrome and the canvas chart update in the same frame — no manual synchronisation needed.

Drill-level tonal variation

The chart uses three levels of the M3 tonal palette to indicate depth as you drill down:

Level Token Visual effect
Year (12 months) --mat-sys-primary Dark green — the strongest tone, anchoring the top level
Month (4–5 weeks) --mat-sys-primary-container Light green — softer, signalling you're one level deeper
Week (5 days) --mat-sys-tertiary-container Teal — a different hue entirely, marking the detail level

This tonal shift is a visual cue that works alongside the breadcrumb and live-region announcements. You can tell at a glance which level you're looking at, even without reading the title.

Why M3 tokens?

The demo uses Material 3-style --mat-sys-* custom properties to show how theme values can pass from CSS through JavaScript to the WebAssembly renderer. Any framework that can read CSS custom properties can provide the same inputs.

It uses raw CSS custom properties so the example does not depend on a particular framework or styling library.

Light and dark themes

Light theme tokens are defined on :root. Dark theme overrides live on body.dark. The toggle button adds or removes the dark class — JavaScript re-reads getComputedStyle(document.body) and passes the new values to WASM. Both the DOM chrome and the canvas repaint in the same frame.

Because M3 HCT defines light and dark variants from the same seed colour, contrast ratios are guaranteed in both themes without manual checking.

Architecture

Rust renders pixels and returns semantic geometry. JS orchestrates state, DOM, events, and accessibility. CSS tokens bridge both — canvas can't read CSS, so JS reads computed values and passes them across the WASM boundary as JSON.

Data flow

CSS tokens → JS readTheme() → JSON → WASM render() → canvas pixels + SemNode[] → JS mirror-dom → overlay divs + sr-only table + live region

Components

Component Language Responsibility
Flare libraries (reusable, any canvas app can depend on these)
flare-chart Rust (rlib) Web bar chart: theme, rendering, tick math, and animation with prefers-reduced-motion. Re-exports flare-core.
flare-core Rust (rlib) SemNode struct (geometry + semantics), Describable trait. Platform-agnostic — pure Rust + serde, no web deps.
mirror-dom JS (ES module) Takes SemNode[], builds overlay divs, sr-only data table, live region. Framework-agnostic, no build step.
Flare Demo (web demonstration of the reusable libraries)
flare-demo Rust (cdylib) WASM bindings: render, render_animated, create_canvas. Implements Describable. Built with --out-name flare.
app.js JS Navigation stack, drill-down, breadcrumbs, streaming, theme toggle, keyboard handlers, mirror-dom wiring.
style.css CSS M3 design tokens (--mat-sys-*), light/dark themes, reduced motion, dyslexia spacing, background tints.

Key design decisions

Decision Why
flare-chart is rlib only (no #[wasm_bindgen]) Avoids WASM name collisions — only the consumer crate exports bindings
Reduced motion read in Rust, not just JS Consumers get correct behaviour by default, even if they forget the JS check
